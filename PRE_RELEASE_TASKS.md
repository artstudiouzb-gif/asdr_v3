# Актуальный статус перед релизом ArtStudio CMS

Документ синхронизирован с `main` 7 сентября 2026 года, после независимого
аудита готовности (см. раздел ниже). Кодовых блокеров нет; здесь остаются
только действия, зависящие от конкретного production-сервера и реального
контента. Полный порядок запуска находится в
[`docs/RELEASE.md`](docs/RELEASE.md), технический деплой — в
[`docs/DEPLOY.md`](docs/DEPLOY.md).

## Закрыто в коде

- Прямой доступ к служебным PHP/SQL/config-файлам блокируется правилами
  Apache/nginx и CLI-guard; ручная проверка production URL описана в
  [`SECURITY.md`](SECURITY.md).
- Полный бэкап БД и загрузок, SHA-256, ротация «7 дневных + 4 недельных» и
  восстановление реализованы в `app/Console/backup_worker.php` и
  `database/restore.php`.
- Heartbeat воркеров, `/health`, статусы `failed`, ретраи и Telegram-алерты
  реализованы для фоновых очередей.
- Вложенное меню, библиотека из 41 типа блоков, Columns, варианты reveal,
  SVG-иконки, ревизии блоков и предпросмотр черновиков реализованы.
- CI выполняет четыре содержательные задачи (`ci.yml`): PHP 8.4–8.5 +
  MySQL 8 / MariaDB, PHPStan уровня 7 + `composer audit`, JavaScript syntax +
  сканеры ассетов и секретов, browser smoke Chromium (включая визуальные
  регрессы и axe-аудит доступности). Ещё два джоба — `legacy-check-82` и
  `legacy-check-83` — ничего не проверяют: это заглушки, закрывающие старые
  обязательные проверки branch protection, поскольку минимум проекта 8.4.
  Отдельно идёт CodeQL (`codeql.yml`). Текущий объём — 1612 сценариев:
  1385 выполняются без БД, ещё 227 требуют `TEST_DB_*` и прогоняются в CI.

## Независимый аудит готовности (7 сентября 2026)

**Заключение: система готова к production.** Критических проблем не найдено.
Две важные находки и четыре улучшения исправлены и влиты в `main` (#346).

Что проверялось собственными измерениями, а не доверием к существующим тестам:

| Направление | Метод | Результат |
|---|---|---|
| SQL-инъекции | обход всех точек интерполяции в запросах | 0 находок: динамические фрагменты только из whitelist-массивов, идентификаторы через `intval`/плейсхолдеры |
| XSS | 29 payload'ов через `HtmlSanitizer`, включая mXSS (`noscript`, `xmp`, `listing`, `mglyph`, `form`-вложение) | 0 обходов |
| SVG | 9 payload'ов через `Uploader::sanitizeSvgString`, включая namespace-префиксы и CDATA | скрипты и `on*` вырезаются |
| CSRF | скрипт по всем POST-маршрутам | 195 из 198 с проверкой; 3 исключения (`/_vitals`, `/push/*`) осознанные, документированы, с rate-limit |
| Авторизация | скрипт по всем `/admin/*` и `/repo/*`, GET и POST | 0 незащищённых маршрутов |
| Эскалация прав | граница `editor`/`admin` на `custom_css`, `custom_js`, блок «HTML» | закрыта во всех путях, включая восстановление ревизии и импорт шаблона |
| Настройки блоков | сверка «реестр → форма → шаблон» | 0 дрейфа: нет мёртвых настроек в админке и неуправляемых возможностей на фронте |
| Типографика | подсчёт по собранному `public.min.css` | 10 статичных `px` на весь бандл против 1700+ через токены шкалы |
| Незавершённое | поиск `TODO`/`FIXME`/`HACK` по `app/` и `templates/` | 0 |

Исправлено по итогам аудита (#346):

- **Canonical** собирался из одного пути, поэтому `/news?page=7` и рубрикатор
  `?category=<slug>` объявляли себя дублями первой страницы —
  `SeoHelper::canonicalUrl` добавляет закрытый список значащих параметров.
- **Принуждение HTTPS** отсутствовало в коде и в обоих `.htaccess`, а
  `release_check` сверял только строку `APP_URL` — теперь выводится из
  `app.url` и проверяется опросом самого сайта.
- Доступность портала `/repo`, персонализированный ответ в общем кеше, цена
  страницы 404 и узкое покрытие проверки горизонтальной прокрутки.

Чего аудит **не** покрывал и что остаётся за ручной проверкой на боевом
сервере: работа админки под нагрузкой и «на клик», адаптивность на реальных
устройствах, фактическое восстановление из бэкапа, живые интеграции SMTP и
Telegram, замер Lighthouse. Эти пункты перечислены в списках ниже.

Известные границы автоматических проверок, о которых стоит помнить при
развитии: проверка горизонтальной прокрутки в CI работает на пяти страницах
из девяти (остальные требуют демо-комплекта в фикстуре), а
`phpstan-baseline.neon` несёт 577 замороженных находок — из них около 508
упираются в нетипизированный `PDO::fetchAll()`. Это посчитанный долг с
храповиком (тест 293 не даёт числу расти), а не риск.

## Обязательно перед открытием сайта

- [ ] Указать боевой `APP_URL`, `APP_ENV=production`, `APP_DEBUG=false`.
- [ ] Направить DocumentRoot на `public/` либо проверить актуальные `.htaccess`.
- [ ] Установить HTTPS. Редирект HTTP → HTTPS включается сам, как только
      `APP_URL` объявлен через `https://` (`RequestUrl::httpsRedirectTarget`);
      факт проверяет `release_check.php` строкой `https_redirect` — она
      опрашивает сайт по `http://` и требует 301/308 на `https://`.
- [ ] Проверить, что служебные URL из `SECURITY.md` возвращают 403/404.
- [ ] Настроить cron всех воркеров и убедиться, что `/health` возвращает `ok`.
- [ ] Снять эталон целостности: `php app/Console/integrity_check.php --baseline`
      и поставить почасовой cron (`DEPLOY.md` §6).
- [ ] Настроить внешнее хранилище бэкапов и выполнить тестовое восстановление
      (`database/restore.php` в отдельную БД — ставит отметку, которую потом
      сторожит `release_check.php`; повторять раз в квартал).
- [ ] Настроить SMTP и Telegram, проверить вход с 2FA и доставку уведомлений.
- [ ] Прописать DNS-записи SPF, DKIM и DMARC для почтового домена и селектор в
      `mail.dkim_selector` (`DEPLOY.md` §10); убедиться, что `release_check.php`
      показывает `mail_dns: OK`.
- [ ] Зафиксировать решения по персональным данным: юрисдикция хостинга и
      бэкапов, регистрация базы ПДн, включать ли аналитику и CDN
      (`SECURITY.md`, раздел «Персональные данные и внешние сервисы»).
- [ ] Заменить демо-контакты, изображения и материалы реальным контентом.
      Страницы «Об Агентстве», «Руководство» и профили руководителей уже
      готовы фикстурой — применяются командой
      `php database/seed_agency_content.php` (сначала `--dry-run`).
      После неё остаётся загрузить фотографии руководителей и добавить
      контактный телефон/почту приёмной в блоки «Профиль персоны».
- [ ] Создать политику конфиденциальности и проверить формы согласия.
- [ ] Проверить sitemap, robots, canonical, Open Graph и редиректы старых URL.
- [ ] Включить OPcache, gzip/brotli и HTTP/2 на сервере.
- [ ] Добавить `/health` во внешний uptime-мониторинг.

## Проверки перед публикацией

```bash
php scripts/release_check.php
php tests/run.php
php scripts/smoke.php https://ваш-домен
```

После загрузки новой версии используйте fail-fast сценарий:

```bash
php scripts/release.php https://ваш-домен
```

Он проверяет окружение, создаёт бэкап, применяет миграции, обновляет шифрование
секретов, очищает кеш и запускает smoke. Доставку кода (`git pull`, архив или
панель хостинга) нужно выполнить отдельно до запуска сценария.

## После запуска

- [ ] Первую неделю контролировать `/health`, `storage/logs/error.log`, журнал
      действий и список недавних 404.
- [ ] Проверить фактическое восстановление последнего production-бэкапа.
- [ ] Замерить Lighthouse; целевой ориентир главной — Performance не ниже 90.
- [ ] Проверить очереди почты, соцсетей, Web Push и вебхуков на реальных
      интеграциях.
