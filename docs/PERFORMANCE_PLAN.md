## Приоритет 1 — критичное, отдача за часы

### 1.1. Глобальный `transition` на `div` и `span`

`public/assets/css/gov-theme.css:62`

```css
body, header, aside, section, div, footer, input, select, textarea, button, a, span {
    transition: background-color 0.35s ease, color 0.35s ease, border-color 0.35s ease, box-shadow 0.35s ease;
}
```

Правило доезжает до собранного `public.min.css` (проверено). Это самый дорогой
селектор на сайте: браузер заводит четыре анимируемых свойства **на каждый
`div` и `span` документа** — на типовой странице это тысячи элементов. Следствия:

- любое переключение класса (`is-scrolled` у шапки при скролле, `is-open` у меню,
  смена темы, открытие a11y-панели) запускает переходы по всему поддереву;
- `box-shadow` в списке — анимация тени всегда идёт через перерисовку, а не
  композитор; на больших контейнерах это перекраска целого экрана;
- смена темы вместо мгновенной становится 350-мс перекраской всего документа —
  это и есть «подтормаживание» тумблера темы.

**Что сделать.** Убрать правило. Плавность смены темы вернуть временным классом
на `<html>` (`theme-init.js` / `asdrSetTheme` вешает `.is-theme-switching` на
350 мс), а точечные переходы оставить там, где они осмысленны — кнопки,
карточки, ссылки, поля ввода:

```css
:root.is-theme-switching, :root.is-theme-switching * {
    transition: background-color .3s ease, color .3s ease, border-color .3s ease;
}
a, button, .btn, [class*="-card"], input, select, textarea {
    transition: background-color .2s ease, color .2s ease, border-color .2s ease, box-shadow .2s ease;
}
```

**Ожидаемый эффект.** Оценочно: главный вклад в INP и в стоимость скролла;
самая дешёвая правка с самым заметным результатом. Мерить `INP` и «Avoid
non-composited animations» в Lighthouse.

**Риск.** Средний: часть плавностей визуально пропадёт. Пройти smoke + глазами
проверить шапку, меню, карточки, тумблер темы, a11y-панель.

### 1.2. `Vary: Cookie` убивает общий CDN-кэш

`app/Core/PublicResponseCache.php:71`

```php
header('Vary: Accept-Encoding, Cookie');
```

Публичная часть ставит cookie `a11y` — это `http_build_query()` от нормализованных
настроек (`A11ySettings::COOKIE`, `:127`): размер текста, контраст, шрифт,
интервалы, режим чтения, скрытие картинок, остановка анимаций, подчёркивание
ссылок. Плюс `site_lang`. При `Vary: Cookie` каждое уникальное сочетание
cookie — отдельная запись в CDN.

**Поправка к первой редакции этого документа.** Изначально здесь было сказано,
что кэш дробится «практически до нуля». Проверка показала, что это
преувеличение: уникальных для посетителя cookie на публичке нет. Сессия
стартует только при наличии своей cookie (`bootstrap.php:135`) и такие ответы
и так не кэшируются; аналитика хранит согласие в `cookie_consent=1` — одно
значение на всех. Реальных вариантов немного: пусто, `site_lang` (2–3
значения), `cookie_consent`, плюс длинный хвост от тех, кто пользовался
панелью отображения. То есть кэш дробится в разы, а не в сотни раз. Проблема
настоящая, но масштаб был назван неверно.

Комментарий в коде объясняет `Vary: Cookie` необходимостью не отдавать
закэшированную языковую копию мимо редиректа в `Router::resolveLocale()`. Задача
настоящая, но решается точнее.

**Что сделать (варианты, по возрастанию сложности):**

1. Сузить ключ до языка. На BunnyCDN/Cloudflare — cache key по cookie `site_lang`,
   а `Vary` оставить `Accept-Encoding`. Настройка на стороне CDN, кода не трогает.
2. Убрать язык из cookie-зависимости ответа: язык уже в URL (`/ru/…`, `/uz/…`),
   а `site_lang` влияет только на редирект с «голого» пути. Тогда кэшируемым
   делать только локализованные URL, а `/` (где происходит выбор языка) отдавать
   `private, no-store`. Это правильный по существу вариант.
3. a11y-настройки перевести с cookie на `localStorage` + применение классов
   в `theme-init.js` (он уже синхронный в `<head>`, мигания не будет). Тогда
   cookie на публичке остаётся только языковой. Требует переноса
   `A11ySettings::htmlAttributes()` с сервера на клиент — самый большой объём.

**Сделано (вариант 2 плюс часть 3).** Реализовано так:

1. `Router::resolveLocale()` — редирект по сохранённому языку теперь работает
   **только на корне** сайта и корнях языков (`/`, `/uz`). На конкретной
   странице выигрывает язык из URL. Побочно чинится и поведение: ссылка на
   `/uz/news/x`, присланная человеку с русской настройкой, больше не уводит
   его на `/news/x`.
2. `theme-init.js` — синхронный скрипт в `<head>` теперь сам расставляет
   `data-a11y-*` из cookie **до первой отрисовки**. Сервер печатает их
   по-прежнему (работает и без JS), но общий ответ из CDN тоже приходит
   правильным, без вспышки «обычный размер → крупный».
3. `PublicResponseCache` — корни языков исключены из кэша (там ещё решает
   cookie), для остальных адресов `Vary: Accept-Encoding`. **Исключение:
   узбекские страницы сохраняют `Vary: Cookie`** — узбекская кириллица
   получается транслитерацией готовой страницы на сервере
   (`View::wantsCyrillic`), и клиент это повторить не может.

**Ожидаемый эффект.** Русские и английские страницы (основная масса трафика)
становятся полноценно кэшируемыми на CDN: повторный запрос отдаётся с edge
вместо полного PHP-цикла.

**Что осталось.** Настроить на CDN ключ кэша по `site_lang` — тогда и
узбекские страницы перестанут дробиться по остальным cookie. Это конфигурация
на стороне BunnyCDN/Cloudflare, кода не требует.

### 1.3. Ассеты вне общего бандла не минифицировались

Файлы, подключаемые не на каждой странице, в `scripts/build-assets.mjs` не
упоминались вообще и отдавались исходниками. Самый крупный случай — блок
«Мониторинг 2030»: 160 КБ CSS и 120 КБ JS без минификации.

**Сделано.** В `build-assets.mjs` добавлен второй, «поблочный» проход: каждый
файл из `AssetCollector` (`JS_MAP`, `CSS_MAP`, `THEME_PART_MAP`)
минифицируется в `*.min.css`/`*.min.js`, хэши уходят в манифест,
`FrontendAssets::blockAsset()` подставляет минифицированный путь, когда
включена сборка бандлов. Заодно это починило `npm run check:assets`: раньше
проверка актуальности этих файлов не покрывала.

**Сам блок «Мониторинг 2030» из системы удалён** по решению владельца — см.
раздел 4. Механика минификации осталась и работает на вынесенных частях темы.

### 1.4. Тело статьи рендерится дважды на каждой новости

`app/Views/site/news_show.php:689` — оверлей режима чтения выводится
**безусловно** (только с атрибутом `hidden`), и внутри него на `:731` повторно
печатается `$contentHtml`, на `:719` — обложка, на `:710` — второй `<h1>`.

Следствия: удвоенный HTML и удвоенное число DOM-узлов на всех новостях (а это
самые посещаемые страницы) плюс лишний `<img>` без `width/height` и без
`loading="lazy"`.

Второй `<h1>` при этом **не** является ошибкой доступности: пока оверлей
закрыт, он под атрибутом `hidden` и в дерево доступности не попадает, а когда
открыт — соседние узлы получают `inert` (`setReaderIsolation`), и из дерева
уходит основной заголовок. В каждый момент экспонирован ровно один `h1`. Это
сделано аккуратно, трогать не нужно.

**Что сделать.** Тело статьи (основная масса разметки) из оверлея убрать и
клонировать из основной статьи при первом открытии — `frontend.js:1778` уже
держит ссылку на оверлей. Заголовок, подзаголовок и лид оставить в разметке:
это несколько сотен байт, а клонирование их усложнило бы код без выигрыша.
Обложку внутри оверлея пропустить через `Media::picture()` с `lazy`.

**Ожидаемый эффект.** HTML новости примерно вдвое меньше; меньше DOM →
дешевле стиль и layout. Без JS режим чтения и так не работает, так что
прогрессивное улучшение не нарушается.

## Приоритет 2 — структурное, отдача за дни

### 2.1. Разрезать общий CSS-бандл

Точная разметка `gov-theme.css` по верхнеуровневым правилам (1834 правила, 331 КБ):

| Область | Правил | Размер |
|---|---|---|
| `newsdetail` / `relnews` — **только детальная новость** | 256 | **42 КБ** |
| шапка/меню/submenu/topbar | 200 | 40 КБ |
| слайдер/hero | 106 | 20 КБ |
| team/person/bio | 56 | 10 КБ |
| альбом/галерея | 32 | 4 КБ |
| a11y-панель | 12 | 3 КБ |
| общее: токены, типографика, карточки, сетки | 1166 | 208 КБ |

42 КБ стилей детальной новости приезжают на главную, где ни одного из этих
классов нет. Механизм для исправления в проекте уже есть и работает —
`AssetCollector` (`CSS_MAP` — самостоятельные блоки, `THEME_PART_MAP` — части темы).

**Шаг 1 сделан.** `newsdetail`/`relnews` вынесены в
`public/assets/css/blocks/news-detail.css`, подключаются из `NewsController`
на детальной новости и на списке. Результат: общий бандл
**419 334 → 383 180 Б** raw (53,6 → 49,7 КБ brotli), вынесенная часть — 6,1 КБ
brotli только на новостных страницах.

Две вещи, которые выяснились при этом и важны для следующих шагов:

- **«Только на своей странице» надо проверять по разметке, а не по имени
  класса.** Первый вариант выноса сломал бы три места: `.relnews-card*`
  использует список новостей (`_news_list.php`), `.newsdetail-subscribe*` —
  виджет подписки (может стоять в сайдбаре любой страницы), а
  `.newsdetail-article__content` и `.newsdetail__badge` — страница проекта.
  Эти три семейства оставлены в общей теме; тест 235 стережёт.
- **Порядок в каскаде надо сохранять.** Вынесенный файл нельзя подключать
  наравне со стилями блоков: те выводятся **после** дизайн-CSS из админки, и
  настройки раздела «Дизайн» перестали бы действовать на новостях. Заведён
  отдельный слот `AssetCollector::requireThemePart()` / `renderThemeStyles()`,
  который выводится сразу после бандла и **до** дизайн-CSS — там же, где
  правила лежали внутри темы. Порядок проверяется тестом.
  Отдельно пришлось перенести сброс `@media (hover: none)` для
  `.newsdetail-photos__item:hover`: он жил в общем блоке темы, а после выноса
  проигрывал бы по порядку — при тапе плитка «залипала» бы приподнятой.

**Шаг 2 сделан частично: вынесена оргструктура** (`blocks/org-structure.css`,
2,0 КБ brotli). Дальше — важная поправка к первоначальному замыслу.

### Насколько мелко резать: замеры

Разложил каждое правило публичного CSS по тому, в каких шаблонах реально
встречаются его классы (сопоставление имён классов с `templates/`,
`app/Views/`, `app/Core`, `app/Controllers`, публичным JS):

| Категория | Объём | Доля |
|---|---|---|
| хром: шапка, подвал, меню, панели | 118 КБ | 25 % |
| общее: встречается во многих местах | 93 КБ | 20 % |
| правила без классов (теги, `:root`) | 28 КБ | 6 % |
| **итого нужно на каждой странице** | **239 КБ** | **51 %** |
| принадлежит ровно одному блоку конструктора | 134 КБ | 29 % |
| принадлежит ровно одной странице (вью) | 55 КБ | 12 % |
| прочее (несколько блоков, динамические имена) | 38 КБ | 8 % |

Но 134 КБ «ровно одного блока» — верхняя оценка. Если требовать, чтобы класс
**не встречался больше нигде** (ни в другом шаблоне, ни в партиале, ни в JS,
ни в `BlockRenderer`, который часть имён собирает конкатенацией), остаётся
**64 КБ на 18 блоков — в среднем 3,5 КБ на блок, то есть меньше 1 КБ brotli
каждый**.

**Вывод: резать по одному файлу на блок не надо.** Файл на 600 байт brotli —
это ещё один блокирующий запрос в `<head>`, и на типовой странице с 5–8
блоками такой разрез скорее вредит. Разрез окупается, когда **стилей много И
поверхность редкая**. По этому критерию:

- `news-detail` — 5,4 КБ brotli, только новости. Вынесено.
- `org-structure` — 2,0 КБ brotli, одна-две страницы. Вынесено.
- `hero` — 9 КБ, но hero почти на каждой странице: выносить бессмысленно.
- остальные блоки — по 1–4 КБ raw, поодиночке не окупаются.

**Что это значит для дальнейшей работы.** Резерв разреза почти исчерпан:
после двух выносов бандл 419 334 → 376 027 Б (53,6 → 49,0 КБ brotli), и
оставшиеся ~49 КБ — это в основном те самые 51 %, которые нужны везде.
Дальше уменьшать надо не разрезом, а **чисткой общего ядра** — раздел 3.1
(473 `!important`, 196 размеров шрифта, 171 тень). Эта работа уменьшает
страницу для всех, а не перекладывает байты между файлами.

**Риск разреза.** Оказался выше, чем я оценил, и дважды сработал:

1. `.relnews-card*` используется списком новостей, `.newsdetail-subscribe*` —
   виджетом подписки в любом сайдбаре, `.newsdetail-article__content` —
   страницей проекта. «Только на своей странице» надо проверять по разметке.
2. Групповой селектор вида
   `.newsdetail-photos__item:hover, .album-card:hover, .btn:hover` содержит
   искомое имя, но уносить его нельзя — карточки и кнопки на остальных
   страницах молча теряют правило. Первая версия извлекателя так утащила
   `.block-hero__subtitle`.

Оба класса ошибок теперь ловятся автоматически: `scripts/split-theme-part.mjs`
уносит правило, только если **каждая** часть группового селектора принадлежит
семейству, а тест 235 проверяет вынесенные файлы на чужие правила.
Визуальная сверка при этом всё равно обязательна.

### 2.1a. Как выносить следующую часть темы

Механика уже собрана, добавление новой части — три шага:

```bash
# 1. Вынести семейство правил (сохраняет порядок, не трогает групповые
#    селекторы, где есть чужие классы)
node scripts/split-theme-part.mjs <имя-файла> '<регулярка>' ['<исключения>']

# 2. Строка в AssetCollector::THEME_PART_MAP и в blockSources сборщика.
#    Если ключ совпадает с типом блока — подключение произойдёт само:
#    PageController уже прогоняет типы блоков страницы через requireJs().

# 3. Пересобрать и проверить
npm run build:assets && php tests/run.php
```

Перед выносом обязательно: `grep -rl '<префикс-класса>' templates/ app/Views/`
— и убедиться, что за пределами своей поверхности классов нет. Тест 235
поймает чужие правила внутри файла, но не поймает случай, когда семейство
целиком нужно ещё где-то.

### 2.2. Бюджет CSS в CI, чтобы бандл не отрастал обратно — СДЕЛАНО

Было: бюджет `cssBrotli: 80 * 1024`, превышение печаталось предупреждением и
ничего не блокировало. Комментарий рядом честно объяснял, почему исключение
убрали: оно ломало сборку при каждом расширении темы. Результат — 419 КБ,
накопленные полутора десятками дизайн-коммитов подряд (`#98`…`#114`).

**Что сделано.** Порог стал жёстким, но только в режиме проверки:

- `node scripts/build-assets.mjs --check` (то есть `npm run check:assets`, то
  есть CI) при превышении печатает ошибку и завершается кодом 1;
- обычный `npm run build:assets` печатает предупреждение и работает дальше.

Это снимает исходное возражение: локальная сборка больше не встаёт посреди
работы над темой, а рост всё равно не проедет в `main` молча.

Потолки взяты от факта с небольшим запасом, а не «с потолка»: CSS 52 КБ при
факте 49.3 КБ, JS 15 КБ при факте 13.3 КБ brotli. Опускать их по мере чистки;
поднимать можно, но в том же коммите объяснив, чем рост оправдан.

Блочные файлы (`AssetCollector`) остались с мягким бюджетом 8 КБ на файл —
предупреждение в любом режиме. Их грузит часть посетителей, а не все, поэтому
и цена роста другая. Самый крупный сейчас — `news-detail.css`, 5.2 КБ.

Обе ветки проверены искусственным занижением порога: `--check` падает с кодом
1, обычная сборка предупреждает и отдаёт код 0.

### 2.3. Индексы для публичных выборок — СДЕЛАНО

Миграция `2026_08_11_public_listing_indexes.sql`. Проверки идут через
`information_schema`, а не `ADD KEY IF NOT EXISTS`: этого синтаксиса нет в
MySQL 8, а миграция должна применяться и там. Повторный запуск безопасен.

```sql
projects     KEY idx_projects_listing (status, deleted_at, is_featured, sort_order, created_at)
photo_albums KEY idx_albums_listing   (is_published, created_at)
videos       KEY idx_videos_listing   (is_published, sort_order, created_at)
news         KEY idx_news_listing     (status, deleted_at, published_at)   -- вместо idx_news_status_published
```

**Две поправки к тому, что здесь стояло раньше.**

1. У `photo_albums` и `videos` нет колонки `status` — там `is_published`.
   Индексы из прежней редакции этого раздела просто не создались бы.
2. Индекс проектов без `is_featured` бесполезен. Полный список
   (`Project::published`) отдаёт бо́льшую часть таблицы, и оптимизатор для него
   правильно выбирает полный скан — индекс он не берёт вовсе (проверено
   EXPLAIN на 1000 строк: `type: ALL`). Выигрыш есть только у запросов с
   `LIMIT`, а на главной это `forHome` с `is_featured = 1`: с колонкой в
   индексе — `type: ref`, `rows: 1` вместо скана 1000.

Что показал EXPLAIN после миграции:

| Запрос | Было | Стало |
|---|---|---|
| `news` лента, `LIMIT 9` | скан + filesort | `ref` по `idx_news_listing`, filesort снят |
| `photo_albums` листинг, `LIMIT 12` | скан + filesort | `range`, filesort снят |
| `videos` избранное | скан | `range` (filesort остаётся: `sort_order ASC, created_at DESC`) |
| `projects` главная | скан 1000 | `ref`, `rows: 1` |
| `projects` полный список | скан | скан — так и надо |

Смешанные направления сортировки (`sort_order ASC, created_at DESC`) индекс
полностью не снимает: filesort остаётся, но получает на вход только отобранные
строки, а не всю таблицу.

Не забыть при следующей миграции: колонки и файл добавить в
`database/schema.sql` (и в `INSERT INTO migrations`), иначе падает тест
консистентности.

**Честная оценка эффекта.** При нынешних объёмах контента — единицы
миллисекунд. Делать стоило как страховку на вырост: сейчас это одна дешёвая
миграция, через год при тысячах записей — уже инцидент.

### 2.4. `content-visibility` для длинных страниц — ОТКЛОНЕНО ПО ЗАМЕРУ

Идея: в публичном CSS нет ни одного `content-visibility`/`contain`, а страницы
оргструктуры, лент и «Об Агентстве» длинные — браузер считает layout и paint
для всего, что ниже экрана.

Реализовано и **откачено**: измеримой пользы нет.

**Как мерилось.** Chromium (CDP `Performance.getMetrics`), сумма
`RecalcStyleDuration + LayoutDuration` за загрузку, вьюпорт 390×844,
`content-visibility: auto; contain-intrinsic-size: auto 600px` на всех блоках
страницы кроме первого.

| Заход | `/` | `/o-nas` |
|---|---|---|
| 1. Без чередования порядка (5 прогонов) | −44 % | −38 % |
| 2. С чередованием порядка (12 пар, медианы выборок) | −4,4 % | −10,9 % |
| 3. То же, **парная** разница | **+0,8 %** | **+1,2 %** |

Третья строка — правильная: сравниваются два замера одной и той же страницы,
сделанные подряд, а не медианы двух шумных выборок. `content-visibility`
выиграл в 4 из 12 и 6 из 12 пар — это монетка. Первый заход дал −40 % не
потому, что стало быстрее, а потому что вариант всегда мерился **вторым**, на
прогретой машине.

Почему пользы нет, если по описанию должна быть: страницы здесь 3–10 экранов
при 6 блоках, и стоимость первой отрисовки определяется первым экраном и самим
объёмом CSS, а не блоками ниже. Отложенная отрисовка при этом добавляет свой
учёт.

**Что попутно выяснилось — на будущее, если тема вернётся.**

- Переход по адресу с фрагментом ломается: пока блок не отрисован, его высота —
  оценка из `contain-intrinsic-size`, и в замере `#block-24` оказывался почти
  на экран ниже нужного места. Для сайта с оглавлением и ссылками
  `#team-<slug>` это регресс, который придётся гейтить на сервере.
- Обрезки содержимого (`contain: paint` работает как `overflow: hidden`) **не
  случилось**: попиксельное сравнение полностраничных снимков дало 0 % разницы
  на `/analitika`, 0,001 % на `/o-nas`; 8 % на `/` объяснились разным моментом
  ленивой загрузки картинок, высоты страниц совпали до пикселя.

### 2.5. Разгрузить композитор

- 34 `backdrop-filter` и 32 `filter: blur()`. Дороже всего — размытие на
  **липкой** шапке, и оно там есть: `gov-theme.css:449, 458` —
  `backdrop-filter: blur(20px) saturate(180%) !important` у
  `.site-header--container-floating` в обеих темах. Пока шапка на экране,
  браузер на каждом кадре скролла заново размывает всё, что под ней. Это
  самый дорогой отдельный эффект на сайте после правила 1.1.
  Заменить на полупрозрачный фон через `color-mix` (бренд-акцент не
  хардкодить — правило проекта) либо оставить размытие, но снизить радиус до
  8–10 px и убрать `saturate()`, который удваивает стоимость фильтра.
  Если размытие решено сохранить — обязательно проверить на реальном
  Android-устройстве, а не в headless-Chromium.
- **Сделано:** `moon-star-twinkle` у `.site-theme-toggle .theme-star--1/2` шёл
  **постоянно**, не под `:hover` (в отличие от соседних `sun-rays-spin` и
  `eye-pupil-pulse`). Переключатель виден в шапке всегда, то есть композитор не
  простаивал ни секунды даже на неподвижной странице. Ограничен
  `:hover`/`:focus-visible`, как у соседей. Проверено через
  `document.getAnimations()`: в покое анимаций стало на две меньше.
- **Сделано:** `button-shimmer` (блик на кнопке-призраке обложки) анимировал
  свойство `left` — это пересчёт лейаута на каждом кадре, а не работа
  композитора. Переведён на `transform: translateX`. Смещение то же: элемент
  шириной 50 % контейнера проходит 300 % его ширины, то есть 600 % собственной.
  Проверено численно — положение блика совпадает в восьми точках цикла с
  точностью 0,01 px. Соседний `hero-button-sheen` изначально на `transform`,
  его не трогали.
- `will-change` встречается ровно 1 раз — это правильно, наращивать не нужно.

**Замер `backdrop-filter`: где он вообще виден.** Отключал фильтр и считал
разошедшиеся пиксели на полностраничных снимках, с контрольным замером шума
(два одинаковых прогона — ленивые картинки дают до 0,16 %):

| Что отключали | `/` | `/o-nas` | `/analitika` | `/media` | `/news` | `/albums` |
|---|---|---|---|---|---|---|
| шум (контроль) | 0,162 % | 0 | 0,081 % | 0 | 0 | 0 |
| размытие у карточек списков | 0,869 % | 0 | 0,081 % | 0 | 0 | 0 |
| размытие у липкой шапки при скролле | 6,6 % | 20,7 % | 0 | 0 | 0 | 0 |

Читается так: **на пяти страницах из шести размытие карточек не меняет ни
одного пикселя** — за карточкой плоский фон секции, а размытие плоского цвета
даёт тот же цвет. При этом каждая карточка стоит отдельного слоя композитора,
и на странице их десятки. На главной эффект виден (0,87 % против 0,16 % шума),
поэтому снять его глобально нельзя — это уже решение о виде сайта.

**Поправка к моей же поправке.** В прошлый раз я записал, что размытие на
липкой шапке «не активно» — это неверно. Активны три правила:
`body .site-header--sticky.is-scrolled` → `blur(16px)`,
`.site-header--container-floating:not(.site-header--transparent)` →
`blur(20px) saturate(180%)` в обеих темах, и парящая прозрачная шапка до
скролла → `blur(var(--header-floating-blur, 14px)) saturate(160%)`. Первое —
именно тот случай, когда браузер размывает подложку на каждом кадре прокрутки.
По замеру оно видно, так что снимать его вслепую нельзя.

**Решения владельца по этому разделу.**

- Бесконечный блик на кнопках обложки (`hero-button-sheen`, `button-shimmer`)
  **оставлен намеренно**: постоянное движение ведёт взгляд к главному действию
  на обложке. Это осознанный размен, а не недосмотр, — не «чинить» его в
  следующей сессии. Технический дефект внутри него (анимация `left`) уже
  исправлен отдельно и вида не изменил.
- Размытие подложки у карточек и радиус у шапки — **сначала замер на живом
  Android**, потом решение. Headless-Chromium рисует программно и о мобильном
  GPU не говорит ничего.

**Как снять этот замер (протокол).**

1. Телефон по USB, на компьютере `chrome://inspect` → Inspect нужной вкладки.
2. Вкладка Performance, запись ~6 секунд, за это время прокрутить страницу со
   списком карточек (`/news`, `/albums`) сверху донизу пальцем, не флингом.
3. Смотреть три числа: доля кадров дольше 16,7 мс, суммарное время в
   Rendering + Painting, и наличие полос «Composite Layers» на каждый кадр.
4. Повторить на той же странице с временно отключённым фильтром — в
   DevTools это делается без деплоя: вкладка Elements → найти правило с
   `backdrop-filter` → снять галочку; либо в Console выполнить
   `document.head.insertAdjacentHTML('beforeend','<style>.news-card,.album-card,.doc-card,.project-card,.team-card,.person-card,.block-advantages__item,.catcard{backdrop-filter:none!important}</style>')`.
5. Разница в доле долгих кадров и есть цена эффекта. Если она в пределах
   единиц процентов — оставлять как есть; если кадры проседают заметно —
   снимать у карточек, у шапки оставить.

Мерить обязательно на бюджетном устройстве: на флагмане размытие бесплатно
почти всегда, а посетители госсайта приходят не с флагманов.

### 2.6. `theme-init.js` в `<head>` — ОТКЛОНЕНО

Первоначально предлагалось инлайнить этот скрипт с CSP-nonce, чтобы убрать
один запрос из `<head>`. **Реализовано и откачено.**

Тест 171 (`tests/cases/171_inline_script_semantics_test.php`) явно требует
`assert_not_contains('<script nonce=', $header)`: публичная шапка не держит
исполняемых инлайн-скриптов даже с nonce. Это осознанное решение по
безопасности — нонс в `<head>`, где выводятся `site_name`, meta и OG-значения,
делает инъекцию в шапку заметно опаснее.

Цена отказа мала: файл отдаётся с `Cache-Control: immutable`, идёт первым в
`<head>` по уже открытому HTTP/2-соединению, весит 1227 байт. Выигрыш не
стоит ослабления CSP. В коде оставлен комментарий, объясняющий, почему скрипт
обязан быть одновременно синхронным и внешним, — чтобы это не «оптимизировали»
повторно.

### 2.7. Условный `304` для HTML — СДЕЛАНО

`PublicResponseCache::sendConditional()`, вызывается из `View::render()` сразу
после `apply()`. Когда истекает `max-age`, браузер идёт перепроверять — и
раньше получал всю страницу заново, даже если она не изменилась. Теперь
получает пустой `304`: тело (60–75 КБ на здешних страницах) не передаётся.

**Хеш считается от готового тела, а не от `mtime` файла кэша блоков.** Это не
деталь реализации, а то, что снимает опасность, записанную в прежней редакции
раздела: страница с формой получает свежий CSRF-токен на каждый запрос, и по
времени файла ей выдали бы `304` с чужим токеном. От хеша тела такая страница
просто не совпадёт сама с собой и приедет целиком. Списка исключений вести не
нужно — и оказалось, что он не понадобился бы вовсе: `Csrf::token()` стартует
сессию, а ответы с сессией и так помечены `private, no-store` и до ETag не
доходят. Защита получилась двойной, обе половины проверены тестами.

Проверено на стенде: совпадение тега → `304` с нулевым телом, слабый тег
(`W/"…"`) → тоже `304`, чужой тег → `200` с телом. Заголовки `Cache-Control`
и `Vary` на `304` сохраняются. Узбекская страница в кириллице не получает
`304` по тегу латинской версии — тела разные, хеши тоже.

**Чего это не даёт.** Экономится трафик, а не процессор: страница всё равно
собирается, чтобы посчитать хеш. Процессор снимают дисковый кэш блоков и общий
кеш на CDN (1.2). И если на сайте включены счётчики в подвале, их код получает
CSP-nonce на каждый запрос — тело меняется, ETag вместе с ним, и `304` не
сработает. Это деградация без вреда: ответ остаётся правильным, просто полным.

## Приоритет 3 — дизайн-система и UI/UX

Это раздел про качество, а не про килобайты, но именно он определяет, почему
дальнейшие правки CSS будут дешёвыми или дорогими.

### 3.0. Поправка: чистка CSS — это не про байты

В прошлой редакции этого документа (и в моём сообщении владельцу) было
сказано, что после исчерпания разреза ядро уменьшит чистка шкал. **Замеры
этого не подтвердили.**

Что измерено:

- **Механическая минификация уже на пределе.** Прогон текущего набора через
  CleanCSS с полной реструктуризацией (`level: 2` без запретов) даёт
  ровно тот же размер, что и текущая осторожная настройка: 375 953 Б raw,
  48 863 Б brotli. Разница между `level 1` и `level 2` — 10 КБ raw и
  0,7 КБ brotli. Дублирующихся правил, которые можно снять автоматически,
  в исходниках практически не осталось.
- **Токенизация теней** — самое «жирное» место — это 180 объявлений на
  7 898 Б. Сведение к пяти токенам сэкономило бы около 4,6 КБ **до сжатия**,
  то есть в пределах 0,5 КБ brotli: повторяющиеся строки теней brotli и так
  жмёт отлично.
- **Сведение размеров шрифта байты не экономит вообще**: `font-size: 0.92rem`
  и `font-size: var(--step--1)` — declaration одной длины.

**Вывод.** Ядро в 49 КБ brotli — это честные 49 КБ разных правил. Чистка
шкал остаётся нужной работой, но её ценность — **сопровождаемость и
единообразие вида**, а не скорость. Записывать её в план ускорения как
рычаг производительности было ошибкой.

Что из этого следует для приоритетов: если цель — метрики, дальше работают
разделы 2.4 (`content-visibility`), 2.5 (размытие на липкой шапке), 2.7
(условный 304) и 3.2 (метрики фолбэк-шрифтов), а не переписывание темы.

### 3.1. Шкалы нет — отсюда 473 `!important`

Измеренная картина: **196** разных `font-size`, **307** разных значений
отступов, **171** тень, **58** радиусов — при том что `--radius: 12px` в
`:root` объявлен. В списке размеров рядом стоят `.93rem`, `.95rem`, `.96rem`,
`.98rem`, `1.02rem`, `1.025rem`, `1.05rem` — это не решения, а следы ручной
подгонки отдельных компонентов.

Прямое следствие — 473 `!important` в `gov-theme.css`: когда у компонентов нет
общего словаря, единственный способ «победить» соседнее правило — повысить
приоритет. Дальше каждая новая правка требует ещё одного `!important`.

**Чьих это рук дело — проверено, а не предположено.** `git blame` на коммите
до начала этих работ (`3d0b6f1`):

| Файл | строки с `!important` | строки с `font-size` |
|---|---|---|
| `gov-theme.css` | 434 Claude / 15 владелец | 345 Claude / 11 владелец |
| `frontend.css` | 81 Claude / 0 владелец | 121 Claude / 1 владелец |

То есть и разнобой размеров, и лес приоритетов — почти целиком результат
прошлых сессий Claude, а не ручной подгонки владельцем. Формулировка «следы
ручной подгонки» выше это смазывала; оставляю её как описание того, **как**
такие значения появляются, но авторство — вот оно.

Практический вывод, а не самобичевание: за этими значениями не стоит чужого
замысла, который можно ненароком стереть. Чистить можно смелее, чем если бы
их расставлял человек под конкретный макет. И причина известна: правка
вносилась «чтобы стало как надо здесь и сейчас», без общего словаря — ровно
тот механизм, который эта секция и описывает.

**Что сделать.**

1. Ввести токены в `:root` рядом с существующими:

```css
:root {
  --step--1: clamp(0.83rem, 0.80rem + 0.15vw, 0.89rem);
  --step-0:  clamp(1.00rem, 0.96rem + 0.20vw, 1.13rem);
  --step-1:  clamp(1.20rem, 1.13rem + 0.35vw, 1.42rem);
  --step-2:  clamp(1.44rem, 1.32rem + 0.60vw, 1.80rem);
  --step-3:  clamp(1.73rem, 1.54rem + 0.95vw, 2.27rem);
  --step-4:  clamp(2.07rem, 1.78rem + 1.45vw, 2.86rem);

  --space-3xs: 0.25rem; --space-2xs: 0.5rem; --space-xs: 0.75rem;
  --space-s: 1rem;      --space-m: 1.5rem;   --space-l: 2rem;
  --space-xl: 3rem;     --space-2xl: 4rem;   --space-3xl: 6rem;

  --radius-s: 8px; --radius-m: 12px; --radius-l: 20px; --radius-full: 999px;
  --shadow-1: 0 1px 2px rgb(15 23 42 / .06), 0 1px 3px rgb(15 23 42 / .10);
  --shadow-2: 0 4px 12px rgb(15 23 42 / .08);
  --shadow-3: 0 12px 32px rgb(15 23 42 / .12);
}
```

Значения `clamp()` в проекте уже применяются (164 вхождения) — это продолжение
существующей практики, а не новая парадигма.

**Сделано: близкие размеры схлопнуты.**

употребимому** соседу в пределах 2 %, и так до устойчивого состояния. При
равной частоте выигрывает более круглое число.

**Сделано: `!important` снят там, где он ничего не держал.**

В файлах темы было 583 приоритета, стало 357 — снято 226 (39 %). Метод, а не
глазомер:

1. Снимок вычисленных стилей **всех** элементов: 9 страниц × 2 ширины × 2 темы

2. Снятие всех приоритетов разом, кроме интерактивных состояний (`:hover`,

   в покое и проверить их не может, поэтому их не трогали вовсе. Это
   осознанная граница метода, а не недосмотр.
3. Сравнение снимков. Изменилось 1321 элемент из 17 024.
4. Для каждого изменившегося элемента и свойства — поиск правил-кандидатов:
   тех, что объявляли это свойство с приоритетом и чей селектор на элемент
   попадает. Совпадение проверял сам браузер (`el.matches`): писать свой
   разбор селекторов значило бы завести второй, неверный движок CSS.
5. Возврат приоритета только найденным правилам, пересборка, повторный
   снимок. Три прохода: 1321 → 408 → 75 расхождений.
6. Остаток разобран руками: скрипт не смог пропатчить четыре правила, у
   которых перед селектором стоит комментарий. Это `padding-block: 0` у

**Шум пришлось отделить отдельно.** Два одинаковых прогона снимка расходятся
на 74 элемента: медленный зум обложки и пульсация кнопки воспроизведения дают
разные `transform` и `box-shadow` в момент замера. Без этой поправки «осталось
85 расхождений» читалось бы как незакрытый хвост, а на деле там ноль.

**Тесты как спецификация.** Девять тестов упали на отсутствии конкретных
`!important`. Ни один из них я не стал править под факт: все девять — про то,
что настройка из админки или состояние обязаны перебить базовую тему (размер
иконок счётчиков и карточек, цвет цифр поверх градиента, отступ hero-кнопки,
`flex-wrap` у priority-меню, ссылки «Ещё» на прозрачной шапке, фон кнопок CTA,
иконки топбара, активная вкладка медиа). Приоритеты вернул.

**Главный урок: CI поймал то, чего снимок не мог увидеть в принципе.** С
первого захода снято было 335, и браузерный тест упал на печатной вёрстке:
отступы блока в `@media print` перестали побеждать. Снимок берёт страницу в
покое, в экранной медиасреде, без пользовательских предпочтений и без классов,
которые вешает JS, — всё остальное он не проверяет, а значит, ничего про это
и не доказывает.

Поэтому приоритеты возвращены целиком в контекстах, которых снимок не
воспроизводит: `@media print`, `prefers-reduced-motion`, `prefers-contrast`,
`forced-colors`, `(hover: none)`, `(pointer: coarse)` и селекторы состояний
(`.is-*`, `[aria-*]`, `[data-a11y]`, `.no-transition`). Это 118 штук поверх
уже возвращённых. Итог скромнее заявленного вначале: снято 226 из 583, а не
335 — зато проверено.

Контрольное сравнение после всех возвратов: 8 расхождений из 17 024, все
восемь — фазы пульсирующей анимации у кнопки воспроизведения и точек этапов
(значения гуляют в обе стороны). Настоящих — ноль.

### 3.2. CLS от подмены шрифта

Шрифты подключены грамотно (`font-display: swap`, `unicode-range`, preload
только выбранных семейств), но метрики фолбэка не подогнаны:
`size-adjust`/`ascent-override` в публичном CSS отсутствуют полностью
(есть только в `admin.css`, одно вхождение). При `swap` это гарантированный
сдвиг макета в момент подмены — на кириллице с PT Sans/Serif он заметен.

**Что сделать.** Для каждого дефолтного семейства добавить fallback-фейс с
подогнанными метриками:

```css
@font-face {
  font-family: 'PT Sans Fallback';
  src: local('Arial');
  size-adjust: 97%;      /* подобрать замером */
  ascent-override: 92%;
  descent-override: 24%;
  line-gap-override: 0%;
}
```

и подставлять его первым фолбэком в `--font-family` / `--font-heading`.
Проценты подбирать по факту, а не переносить из примера.

базе — `:8001` с кодом до работ (`3d0b6f1`), `:8000` с текущим `main`.
Lighthouse 12.8.2, мобильный пресет, по три прогона, медиана.

**Визуальная сверка:** скриншоты главной, новости, оргструктуры и страницы
руководства на 375/1440 px в светлой и тёмной теме. В светлой теме
оргструктура и руководство — побайтово идентичны; на остальных разница в
десятки-сотни байт и объясняется счётчиком просмотров (1383 → 1387).
Расхождений в вёрстке нет.

### Чего этот замер НЕ показывает

- **Эффект на интерактивность не проверен.** TBT равен нулю почти во всех
  прогонах — демо-страницы слишком лёгкие, а INP Lighthouse не измеряет
  вовсе. Стоимость пересчёта стилей вышла 0,10 мс на обоих стендах: 659
  узлов мало, чтобы разница проявилась. Механизм снятия переходов
  подтверждён, выигрыш в миллисекундах — нет.
- **Абсолютные значения нерепрезентативны**: `php -S` даже с воркерами
  далёк от боевого сервера, FCP около 4 с — свойство стенда.
- **CLS не изменился** (0 на обоих). Более ранние цифры про CLS 0,048 → 0,005
  получены на невалидном прогоне и недействительны.

### Четыре ошибки методики, которые пришлось поймать

Первые заходы давали правдоподобные, но ложные результаты. Если ставить такой
замер заново — проверять именно это:

1. **Разный `APP_DEBUG`** у стендов. Давал ровное отставание ~2 с на запрос
   и выглядел как регресс на 40 %.
2. **`php -S` однопоточен.** Он сериализует запросы, и картинка ждёт за CSS:
   `Load Delay` LCP-картинки доходил до 4,6 с при живом preload. Лечится
   `PHP_CLI_SERVER_WORKERS=8` — и обязательно на обоих стендах.
3. **Старый стенд не отдавал `/uploads`** (симлинк лёг внутрь существующего
   каталога, 404 на все картинки). LCP-элементом становился заголовок вместо
   картинки, и метрика «ухудшалась» ровно потому, что на новом стенде
   картинка появлялась.

Общий признак первых трёх: **LCP-элемент отличался между стендами**. Это и есть
главный индикатор невалидного A/B — сверять его в первую очередь. Проверка
эквивалентности стендов вынесена в `preflight` (коды ответов на картинку, JS
и шрифт; окружение процессов; число `<img>` в разметке).

4. **Порядок измерений** (поймано на 2.4). Если вариант всегда мерится вторым,
   он выигрывает просто потому, что машина прогрелась: `content-visibility`
   «давал» −40 %, а при чередовании порядка и парном сравнении — ноль.
   Правило: чередовать порядок и сравнивать **парные разницы**, а не медианы
   двух выборок. Сравнение медиан здесь показывало −11 % там, где парная
   разница была +1 %. Дополнительная проверка бесплатна: если абсолютная
   база между прогонами скачет (здесь 70 → 147 мс), выборки несравнимы и любой
   вывод из них — про машину, а не про правку.

## 5б. Сбор Core Web Vitals с реальных посетителей

Всё, что мерилось до этого, — лаборатория: Lighthouse на локальном стенде с
демо-контентом. Она не показывает **INP вовсе**, а LCP упирается в дев-сервер.
Главная правка сессии (снятие глобального `transition`) так и осталась
неподтверждённой: TBT на демо нулевой, потому что страницы слишком лёгкие.

Поэтому добавлен сбор с поля.

- Библиотека `web-vitals` (3,3 КБ сжатой) вендорится в
  `public/assets/vendor/web-vitals/` тем же `sync-vendor-assets.mjs`, что и
  Tabler с Coloris. Считать INP руками нельзя: у него своя логика группировки
  взаимодействий, учёта bfcache и скрытых вкладок.
- `public/assets/js/web-vitals-report.js` собирает LCP, INP, CLS, TTFB, FCP и
  шлёт одним `sendBeacon` при скрытии вкладки — к этому моменту INP и CLS уже
  окончательные.
- `POST /_vitals` (`Site\VitalsController`) принимает пачку, проверяет имена и
  диапазоны значений, ограничивает частоту файловым лимитером.
- `App\Core\WebVitals` хранит и считает **75-й перцентиль** — величину, по
  которой оценивают сайт. Среднее здесь бесполезно: его вытягивают быстрые
  заходы с горячим кешем.
- Раздел «Скорость у реальных посетителей» в админке → «Производительность»
  показывает перцентили за 28 дней, отдельно по мобильным.

**Что НЕ собирается:** адрес страницы, IP, User-Agent, идентификатор
посетителя. Только метрика, значение, оценка и три крупных среза — тип
страницы, мобильный/десктоп, язык. Cookie не заводится: он вернул бы ровно ту
проблему с дроблением общего кеша, которую чинили в разделе 1.2. Сессию ручка
тоже не запускает — по той же причине (см. 1.2, находка про `Auth::check`).

**По умолчанию сбор выключен.** Включается в админке; там же задаётся доля
выборки. Хранение — 60 дней, дальше `WebVitals::prune()`.

**Как этим пользоваться.** Включить, подождать неделю трафика, посмотреть
INP на мобильных. Если он в «хорошо» — правка 1.1 подтвердилась; если нет —
искать дальше по разделам 2.4 и 2.5.

### 7.1. Что уже сделано и подтверждено замером

**Обложка и LCP (раздел 10 брифа).** Закрыто целиком:
первый слайд — `eager`, остальные `lazy`; у видео первого слайда

**Шрифты (раздел 13 брифа).** Закрыто, и это исправление к разделу 3.2 ниже:

**Сжатие и кэш (разделы 17, 18 брифа).** `public/.htaccess`: Brotli с откатом

### 7.2. Закрыто частично

1. **AVIF (раздел 9 брифа).** WebP есть, AVIF — нет. Отклонён осознанно
   (раздел 4): выигрыш 20–30 % к WebP, но требует расширения
   `ImageBatchOptimizer`, третьего `<source>` в `Media::picture()` и
   перегенерации всей медиатеки.
2. **Facade для YouTube вне обложки (раздел 11 брифа).** У блока «Текст»,

### 7.3. Что невозможно сделать из контейнера

Разделы 2, 24 брифа требуют замеров на живом сайте, и это же главный принцип
брифа («сначала измерить»). **Сделать их отсюда нельзя:** исходящий HTTPS идёт

Поэтому таблицу «до/после» из раздела 24 брифа заполняет владелец или тот, у

### 7.4. Находки этой проверки

1. **Демо-обложка отдаётся исходным JPEG.** `preload` на главной ведёт на
   `/uploads/public/demo-agency-hero.jpg`, без `imagesrcset`: WebP-вариантов у
   файла нет. Причина не в коде — `Uploader` строит `.webp`, `-800.webp` и
   `-1600.webp` при загрузке через админку, а сидер кладёт файл мимо загрузчика.
   **Практический вывод для боевого сайта:** любая картинка, попавшая в
   `/uploads` по FTP или сидером, отдаётся оригиналом, и если это LCP-элемент —
   это прямая потеря LCP. Лечится разово:
   `php scripts/optimize_images.php --dry-run`, затем без флага.
2. **81 % `public-content-modes.css` — печатные правила, блокирующие рендер.**
   Файл подключается на каждой странице обычным `<link>`; из 5 743 Б
   4 679 Б лежат внутри `@media print`. Разделить на печатный (`media="print"`,
   не блокирует) и экранный — это ~1,1 КБ gzip блокирующего CSS.
   **Делать не стал**: по измеренному в разделе 2.1 критерию файл меньше
   ~2 КБ brotli не окупает отдельного запроса. Записано, чтобы не считать
   заново.
3. **`news-detail.min.css` приезжает на главную** — и это правильно, а не
   регресс: ключ `news_feature` в `THEME_PART_MAP` ведёт на тот же файл,
   потому что крупная карточка новости использует те же классы.
